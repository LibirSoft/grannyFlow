# granny on Cursor and other hosts

Cursor has subagents but no workflow engine, so you run the loop yourself, step by step, with the same prompts and the same rules. It is not deterministic: keep strictly to the steps below and keep a written log in `<workDir>/runs/<date>/journal.md`.

## Install the subagents

Copy `engines/cursor/agents/*.md` to `~/.cursor/agents/` (all projects) or `<project>/.cursor/agents/`, and set `model:` in each file (`inherit` uses the chat's model). Cursor sometimes ignores a subagent's `model:`; check which model actually ran when it matters.

Config: read `~/.config/granny/config.json` and `<repo>/granny.config.json` yourself and apply the layering in [config.md](config.md); only `threshold`, `maxRounds`, `planReview`, `finalReview`, `checks`, `maxRepairs`, `base`, `gates`, `workDir`, `worktree`, `worktreeDir`, `language`, `aiAttribution`, `rules` and `reviewers` apply here - of a reviewer, its `name`, `engine`, `mode`, `focus`, `command`, and `model` where the engine passes it on. An `agent` reviewer runs `granny-reviewer` on whatever model that subagent has.

## The worktree

With `worktree` on (the default), set it up by hand before the first stage - also when you resume with `fromStage` - by the rules the engines follow ([config.md](config.md#worktree)):

1. Add the line `/<workDir>/` to `<common dir>/info/exclude` unless it is there, where `<common dir>` is what `git -C <repo> rev-parse --git-common-dir` prints (relative to `<repo>`).
2. `git -C <repo> worktree list --porcelain`. When a `branch refs/heads/<branch>` line belongs to a `worktree <path>` entry (the main checkout included), that path is the worktree: `git -C <path> status --short` must print nothing. If it prints anything, stop before any subagent runs and tell the user - they commit or discard it, not you.
3. Otherwise, when `git -C <repo> show-ref --verify --quiet refs/heads/<branch>` succeeds: `git -C <repo> worktree add <worktreeDir>/<branch-slug> <branch>`.
4. Otherwise: `git -C <repo> worktree add -b <branch> <worktreeDir>/<branch-slug> <base>`.

`<worktreeDir>` defaults to `<parent of repo>/<repo name>-worktrees`; `<branch-slug>` is the branch with every character other than letters, digits, `.`, `_` and `-` as `-` (`feat/login` → `feat-login`). The "Granny - worktree setup" command in [prompts.md](prompts.md) does all four steps in one go and prints `[granny] worktree: <path>`. From then on the worktree is `<repo>` in every prompt and every terminal command; name it in the report and never remove it. With `worktree: false`, work in `repo` on the branch checked out there.

## Planning

With a `goal` and no stages, after the worktree: delegate to `granny-planner` with the "Planner" prompt from [prompts.md](prompts.md), the plan path filled in (default `<repo>/<workDir>/plans/<branch-slug>.md`). Check with `git status --short` that it committed nothing. Then, with `planReview` on, run the plan review below on the files it returned; report the plan, the proposed stages and the questions, and stop - implement nothing until the user approves ([config.md](config.md#planning)).

## The plan review

The plan review is optional and off by default; enable it with `"planReview": true`. It runs every reviewer, the judge and the implementer over the plan for up to `maxRounds` rounds before any code is written, so it costs extra tokens. With plan files and `planReview` on, review the plan after the worktree and before stage 1; skip it when you resume with `fromStage` above 1 ([config.md](config.md#plan-review)). It is the review loop below, steps 2-5, on the plan instead of a diff, with these differences:

- Reviewers, round N, output `<workDir>/review-plan-review-rN-<name>.md` / `.log`, run from the worktree:
  - engine `codex`, or `auto`: `codex exec --sandbox read-only -o <workDir>/review-plan-review-rN-<name>.md '<prompt>' </dev/null > <workDir>/review-plan-review-rN-<name>.log 2>&1`, with the "Plan reviewer - codex exec, the Codex plugin task and the {prompt} of a command engine" prompt from [prompts.md](prompts.md) as `<prompt>` (shell-quoted, one line).
  - engine `codex-plugin`: `node <companion> task '<prompt>' </dev/null > ….md 2> ….log`, with `CLAUDE_PLUGIN_DATA=<workDir>/codex-plugin-<name>` exported - no `--write`, no `--background`. `Codex did not return a final message.` means it did not run.
  - engine `agent`: `granny-reviewer` with the "Plan reviewer - agent engine" prompt.
  - engine `command`: only a template with `{prompt}`, filled with the same one-line prompt; a reviewer without `{prompt}` sits the plan review out - say so in the journal. No reviewer left → the plan review fails.
- Judge: `granny-judge` with the "Judge - plan review" prompt.
- Fix: `granny-implementer` with the "Implementer - plan fix" prompt. It edits the plan files in place at their absolute paths, adds (round 1) or extends (later rounds) a `## rN deltas (<date>)` section at the top with the date from `date +%F`, and never stages or commits them. Check with `git status --short` that it committed nothing.
- `clean` or `residual-only` → go on to stage 1. `round-cap` or `review-failed` → stop: implement nothing, report the plan findings left unresolved, and wait.

## The loop

Prompts: [prompts.md](prompts.md). Each subagent ends its answer with a JSON block; read that block, not the prose.

For each stage, from `fromStage` on:

1. **Implement.** Read `git rev-parse HEAD` in the worktree yourself and keep it as `startSha` - not the one the implementer reports (when they differ, say so). Delegate to `granny-implementer` with the "Implementer - stage" prompt. Then, when `git rev-list --count <startSha>..HEAD` is 0, the implementer made no commit: read `git status --porcelain` (the work dir and the plan files do not count), and when it lists anything delegate once to `granny-implementer` with the "Implementer - commit" prompt and the status lines (no repair spent), then count again. Still 0: the stage ends `no-changes` without a review (its note names the files still uncommitted), and the stages that build on it (its `after`, or the previous stage in its repo) are not started - they end `skipped` with a note naming it.
   **Checks** - with `checks` in the config ([config.md](config.md#checks)): run each check the stage selects (its `checks` names, default all) yourself in the terminal, from the worktree - `timeout <s> bash -c '<run>'` when it has a `timeout` (`gtimeout` where only that is on PATH, as on macOS with Homebrew coreutils; with neither, stop and tell the user to `brew install coreutils` or drop the `timeout`) - and apply the pass rule: exit 0, and for a `metric` the last match's first capture group is a number within `[min, max]`. Before every run read `git status --porcelain` there (the work dir and the plan files do not count - they stay uncommitted): never run the checks on, or review over, uncommitted work - when it lists anything, delegate to `granny-implementer` with the "Implementer - commit" prompt and the status lines; that spends a repair (against the largest `maxRepairs` of the checks), and when the tree is still dirty with none left the stage ends `checks-failed` with `checks not run at <gate> - uncommitted changes: ...`. When the status cannot be read, read it once more; failing again, never take the tree for clean - the stage ends `checks-failed` with `checks not run at <gate> - working tree status unreadable (<exit code and output>)`, no check run and no repair spent. Without checks, read the status after the implementer and after every fix the same way, give one "Implementer - commit" prompt when it is dirty, and when it stays dirty say so in the stage's note. All green → review. Otherwise delegate to `granny-implementer` with the "Implementer - repair" prompt and every red check's command, exit code, metric note and the last 3000 characters of its output, then run all of them again; when a red check has already had its `maxRepairs` repairs (default the top-level `maxRepairs`, 2) at this point, the stage ends `checks-failed` without a review and the stages that build on it are not started, as after `no-changes` - nor any later stage in that repo, since its red commits are on the branch. Run the checks the same way after every fix in step 5, before the next review round. Never weaken a check to get green, and do not let the implementer do it either.
2. **Review**, round N (N starts at 1; skip the loop when the stage has `review: false`). Run every reviewer in `reviewers` - at the same time where you can (terminal commands in the background, subagents in parallel), otherwise one after another. For a reviewer named `<name>`:
   - engine `codex`, or `auto` (an entry's engine when it names none; here it means the Codex CLI): run in the terminal, from the worktree (the repo with `worktree: false`):
     `codex exec review --base <startSha> -o <workDir>/review-<stage>-rN-<name>.md > <workDir>/review-<stage>-rN-<name>.log 2>&1`
     It can take over 10 minutes; let it finish.
   - engine `codex-plugin`: the same, with the plugin command from [config.md](config.md#the-codex-plugin) (`node <companion> review --wait --base <startSha> --scope branch > ….md 2> ….log`, or `adversarial-review … -- <focus>`), with `CLAUDE_PLUGIN_DATA=<workDir>/codex-plugin-<name>` exported for it. No companion, or no `node` on `PATH`, is a failure. Adversarial findings read `- [high] Title (file:line)`: critical/high/medium/low are P0/P1/P2/P3.
   - engine `agent`: delegate to `granny-reviewer` with the "Reviewer - agent engine" prompt.
   - engine `command`: run the reviewer's `command` from the worktree, with `{base}` = `startSha`, `{out}` = `<workDir>/review-<stage>-rN-<name>.md`, `{model}` = its model, `{prompt}` = the "Reviewer - command engine" prompt - each value shell-quoted.

   Read the findings from `- [P1] Title — file:line` lines (from the `.md`, or what the command printed when the `.md` is empty) and number each reviewer's findings `<name>-F1`, `<name>-F2`, …, noting the reviewer on each. Never invent findings. Output with no such line is clean only when it is just `No findings.` (or the plugin's `No material findings.`, inside the plugin's heading, `Target:` line and, with `Verdict: approve`, its summary paragraph and `Next steps:` and `Reasoning:` lists); a no-findings line next to other text is not clean, so read it: problems it describes in prose are findings, and output that is not a finished review saying the changes have no problems means the reviewer did not run (below).

   A reviewer that exits non-zero, prints that Codex got no usable result, (agent) returns no JSON block, or whose run or subagent call fails with an error did not run: let the other reviewers finish, then run that reviewer once more. If it fails again, the stage ends `review-failed`; name the failed reviewer(s) and keep the findings of the reviewers that ran as unresolved, plus the failed reviewer's findings from the round before - also one that the judge merged into another reviewer's finding.

   No reviewer reported a finding → stage `clean` - unless the implementer, or the last fix, reported red gates and the stage ran no checks: then the stage ends `gates-red`, with the gates in its note.
3. **Route.** Every P0/P1 finding (also critical/high) goes to the implementer as it is - do not give it to the judge - unless a fixer in this loop already declined a finding (listed it in `declined` with its id and reason; `deviations` never counts): then P0/P1 findings go to the judge with the rest.
4. **Judge** - only when there are findings for it. Delegate to `granny-judge` with the "Judge" prompt and only those findings; from round 2 on use "Judge - from round 2 on", listing every finding sent to the fixer so far as `r<N>/<id>` with the ones each round's fixer declined (`r<N>/<id>` and its reason) and that round's deviations as its other notes, and every finding kept as residual so far under its `r<N>/<id>` label. Keep a `repeatOf` it sets only when it names one of those labels. A finding it marks `duplicateOf: <id>` (an id in that same list, not itself, not a cycle) is merged into that finding: report it once, list the merged ids on it, and give it the highest score of the group.
5. **Triage**, exactly: a finding is sent back when its severity is P0/P1 (or critical/high), unless its `repeatOf` names a finding a fixer declined; when the judge gave it no score; or when its score is **strictly greater** than `threshold` (default 70). Everything else is residual for the user - a repeat of a declined finding too, also a P0/P1 one; say so. Residual adds up over the rounds: keep every earlier round's residual finding until the judge marks a later finding as its repeat - drop it when that repeat is sent back, replace it with the repeat when the repeat is residual too - and report the residual of all rounds, also when the stage ends `clean`, `checks-failed` or `round-cap` (there, the last round's findings are unresolved and the earlier rounds' residual stays residual).
   - Nothing to send → stage `residual-only` (`gates-red` when the gates are red, as above, keeping the residual findings).
   - Otherwise delegate to `granny-implementer` with the "Implementer - fix" prompt and only the findings to send - when some of them repeat a finding the fixer declined, with the OVERRULED block of "Implementer - fix, from round 2 on" - keep the ids it lists in `declined` with their reasons for the next judge and the OVERRULED block (only an id you sent it counts; its deviations are notes, never a decline), then go to step 2 with N+1.
   - After `maxRounds` (default 4) reviews without reaching `clean` or `residual-only` → stage `round-cap`; the last round's findings are unresolved.

Dedupe happens only among the findings that are not P0/P1, so a P2 that repeats a P1 is judged on its own; and a reviewer that labels everything P0/P1 reaches the judge only after a fixer declined findings.

After the last stage - unless a stage failed - run the checks once more in each repo that had stages, on the whole branch - every check one of that repo's stages selected (all when one of them lists no `checks`; none when all list `[]`) - with the same repairs, but only when the final review follows and no stage of that repo ended `checks-failed` (otherwise run them once, without repairs); when they stay red the branch is not PR-ready: skip the final review, report `checks-failed` and still do the final check. Then run the final review ([config.md](config.md#final-review)), with `finalReview` on, in every repo that had more than one stage or a merged lane: the review loop above, steps 2-5, named `final review` (`final review <repo name>` in another repo), on the diff from the repo's `<base>` (`codex exec review --base <base>`, `{base}` = `<base>`), with the "Final review" note from [prompts.md](prompts.md) added to every reviewer prompt and the judge prompt; the implementer fixes on the run's branch. A `round-cap` or `review-failed` here does not stop you: report it with the unresolved findings.

Then do the "Granny - final check" yourself - in every repo the stages worked in. With `checks`, when the final check committed anything, run that repo's final checks once more, without repairs; red, or uncommitted files in `git status --porcelain` before or after them (the plan files do not count), means the branch is not PR-ready - say so in the report. Then report per SKILL.md section 5 and wait.

## Parallel stages

The engines run independent stages together ([config.md](config.md#parallel-stages)); here you may do the same when you can run subagents in parallel, otherwise run the stages in list order - the result is the same, only slower. Keep the order rules: a stage starts only after the stages in its `after` (without `after`: the previous stage in its repo). A stage in another repo of `repos` works in that repo's own worktree, set up like the first. A stage that runs while another stage of the same repo is still busy gets its own worktree: `git -C <repo> worktree add -b <branch>--s<N>-<stage-slug> <worktreeDir>/<branch-slug>--s<N>-<stage-slug> <branch>`. After its review loop, and once no stage works in the run's worktree, run `git merge --no-edit <lane branch>` there; on a conflict hand the "Implementer - merge" prompt to `granny-implementer`, and check that `git rev-parse -q --verify MERGE_HEAD` prints nothing afterwards. Then check that `git merge-base --is-ancestor <lane branch> HEAD` exits 0; when it does not, the lane is not merged (a merge can fail without a conflict, for example over uncommitted changes in the run's worktree): stop, leave the lane worktree and branch in place and tell the user. Only then, when the lane has no uncommitted change, `git worktree remove --force <lane>` and `git branch -d <lane branch>`, and tell the user exactly which of the two you could not remove.
