# Changelog

## Unreleased

### Added

- omp (oh-my-pi) host: granny runs as an omp extension (`engines/omp/extensions/granny-workflow/`, installed with `cp -r <skill-dir>/engines/omp/extensions/granny-workflow ~/.omp/agent/extensions/`). In your omp session it adds `granny_run`, `granny_status` and `granny_cancel`, with the inputs, preflight and completion message of the opencode plugin. Every role runs as its own `omp --mode json --no-extensions -e <extension> --approval-mode yolo --session-dir <run dir>/sessions/<n>-<label>` process on its own model (`--model`, `effort` as `--thinking`) and answers through its `granny_submit_*` tool; follow-ups resume it with `--continue`. A `tool_call` guard in each role process blocks `ask`, the `github` tool's `pr_create`/`pr_push`/`pr_checkout`, and `git push`, `git remote add`, `git stash`, `git rebase`, `git reset --hard` and `gh pr` anywhere in a `bash` command; read-only roles may call only omp's reading tools, `bash` (without `git add` or `git commit`) and their submit tool. Transient provider errors back off 30 s, 2 min, 5 min and 10 min, and `granny_cancel` stops every role process and review command by process group. The `omp` host key works in role and reviewer `model` objects, and omp runs no Codex reviewer: `auto`, `codex` and `codex-plugin` (an entry without `engine` included) are refused there - a Codex review is an `agent` reviewer on an `openai-codex/...` model. The steps are in `references/omp.md`.
- `granny setup`: say it to your agent in a project and granny asks about review strictness (presets strict `55`, normal `70`, relaxed `85` for `threshold`), the reviewers it found working (the host model, Codex), the checks from the project's own commands, and where to save, then writes `<repo>/granny.config.json` or `~/.config/granny/config.json`, keeping the keys it did not ask about. It starts no run. The steps are in `references/setup.md`.
- README: install steps come first, followed by `granny setup`, a short usage guide and how the loop works; the full rules, the priority tables and the reviewer examples are in `references/config.md`.
- Review: the judge classifies findings instead of scoring them, and the engine decides with a fixed rule table. For every finding it gets the judge returns `verdict` (`confirmed`/`refuted`/`unverified`), `impact` (`critical`/`major`/`moderate`/`minor`/`none`, judged assuming the trigger happens - likelihood never lowers it), `likelihood` (`common`/`edge`/`rare`), `fixCost` (`trivial`/`small`/`large`), `scope` (`in-scope`/`pre-existing`/`other-stage`), `evidence` (`path:line` plus the trigger steps) and `reason`; its prompt carries the impact rubric with examples. The engine lowers an unverified finding's impact one class (evidence without `path:line` counts as unverified), computes a priority from the impact × likelihood table plus the fix cost, and takes the first matching rule: P0/P1 → fix; not judged or an invalid classification → fix; `refuted`, `other-stage` and `pre-existing` → residual (a `critical`/`major` pre-existing one flagged ATTENTION); impact in the new `alwaysFix` (default `["critical", "major"]`) → fix; priority > `threshold` → fix; else residual `under the bar: <impact>/<likelihood>/<fixCost> -> <priority>`. Each finding keeps its classes, `priority` and `decision: { rule, action, why }` in the log, the fix prompt, `history` and `residual`; merged duplicates keep the strongest copy (a fix one first, then the higher priority). Before, one 0-100 number mixed likelihood, impact and cost, and on a real run a data-corrupting save race (55, then 68), a lock only a reload cleared (68, then 62) and a YAML merge that could publish a draft (55) all stayed under 70 and were never fixed; now they get 95, 80 and 100 and are fixed by rule 6. `threshold` keeps its meaning on the computed priority, so `minor` never passes it (at most 50) and `moderate` only when `common` with a `small` or `trivial` fix.
- Review: a decision ledger crosses review loops, and a ratchet holds repeats to it. Every finding a round sends to the implementer or keeps residual is recorded with its classes, priority, rule and the fixer's decline reason; later rounds see it as EARLIER DECISIONS (it was EARLIER ROUNDS, without the classes or the rule), and the final review's judge sees every stage review's decisions in its repo from round 1 on, labelled `s<k>/r<n>/<id>`. A stage fixer's decline counts in the final review, so a repeat of a declined P0/P1 there goes to the judge. When the judge marks a finding as a repeat (`repeatOf`), the engine raises its impact and likelihood back to the earlier entry's when they dropped - unless it is `refuted` with a `path:line` the earlier evidence did not cite - records it in `decision.raised` and logs `<stage> r<n>: the ratchet raised <id> - repeat of <label>: <what>`. Before, the judge saw only what went to the fixer within one loop, and the same finding swung between rounds and loops (68 -> 62 on the measured run).
- Claude Code: a `helper` role (`roles.helper`, default `{ "model": { "claude-code": "haiku" }, "effort": "low" }`) runs granny's plain commands - the worktree setup, the HEAD, commit-count and status reads, the timeout probe, the checks, a lane's merge and cleanup, and the start, wait, read and stop steps of a Codex or `command` review. A Workflow script has no shell, so each of these is an agent that runs one given command; they ran on `roles.granny`, which defaults to the session model, and on one real run about a third of the tokens went to Opus agents relaying commands such as `git rev-parse HEAD` (about 34k tokens each). `roles.granny` now covers only the extraction fallback and the final PR-ready check, so a `roles.granny.model` set to keep the helper steps cheap does not reach them now - set `roles.helper` for them. The review steps are safe on Haiku because the engine owns the wait loop. opencode runs these commands itself and starts no helper.
- Review: the judge gets one retry before a finding falls to rule 2. When it returned nothing, or left a finding it was given unclassified (left out, a missing field, an unknown value, an empty `evidence`), the engine calls it again with the same prompt plus a RETRY note naming each such finding and what was wrong (label `judge <stage> r<n> retry`; log `<stage> r<n>: judge left <k> finding(s) unclassified - retrying once: ...` or `judge returned nothing - retrying once`), and takes only those findings from the new answer, so a classification that was valid the first time stays. Only findings still unclassified after the retry go to the implementer unjudged, logged `... also on a retry - to the implementer unjudged (rule 2): <id> (<why>)`; the log line for an empty answer now reads `judge returned nothing, also on a retry - all <k> finding(s) go to the implementer unjudged (rule 2)`. Before, one malformed answer sent every finding it touched to the fixer, and Haiku's first try came back malformed in 2 of 8 measured calls.
- Claude Code: `readOnlyAgent` (default `false`) enforces read-only for `agent` reviewers, the judge and the extraction agent. With it on, granny passes `agentType: "granny-readonly"` to their Workflow `agent()` calls; the skill ships that agent definition (`engines/claude-code/agents/granny-readonly.md`: tools Read, Grep, Glob, Bash - no Edit or Write) and a PreToolUse hook (`engines/claude-code/hooks/granny-readonly-guard.mjs`, run with `node`) that, for agent type `granny-readonly`, blocks the write tools and every Bash command other than read-only git (`git diff`, `log`, `show`, `blame`, `status`, `rev-parse`, `merge-base`, `ls-files`, `git branch --show-current`) and read-only shell (`cat`, `sed -n '<from>,<to>p'`, `grep`, `find` without `-exec`/`-delete`/`-fprint`, `ls`, `head`, `tail`, `wc`, `pwd`), with `cd <dir> &&`, pipes and `2>/dev/null` allowed and `$(...)`, backticks, variables and redirection into a file refused. Their prompt then lists those commands after the `READ-ONLY ROLE` line. Before, read-only was only that line on Claude Code, and a reviewer could edit files or `git commit`. It is off by default because the skill install puts neither file where Claude Code looks: copy the agent to `~/.claude/agents/`, the hook to `~/.claude/hooks/` and add the hook to `~/.claude/settings.json` first; a missing agent stops the run at the first reviewer with `agent type 'granny-readonly' not found`. The review-command helpers keep the default agent, since they write the review's `.out`, `.exit` and `.pid` files. opencode ignores the key.

### Changed

- Claude Code: the judge runs on Haiku by default (`roles.judge` is `{ "model": { "claude-code": "haiku" } }`, was `sonnet`); a `roles.judge.model` in any config layer still wins, and opencode keeps the session model. Since the judge only classifies and the engine decides, the classification was measured on 4 real findings, 2 refuted fakes and 1 duplicate, 2 runs per model: Haiku's outcomes matched the user's later fixes on 3/4 findings, Sonnet's on 2/4; both refuted every fake and caught the duplicate, and both gave the same outcome in both runs. Haiku errs toward an extra fix round, Sonnet toward leaving a real bug open (it classified a fail-open `git status` probe `moderate` as a "rare failure case", letting likelihood lower impact), and a Haiku call costs about $0.004 against $0.025. `"roles": { "judge": { "model": "sonnet" } }` switches back for fewer extra fix rounds.

### Removed

- Review: the judge returns only classes and scores nothing. This changes the result shape: the judge's overall `score`, `history[].score` on every review round and a finding's `score` are removed. The numeric per-finding fallback is removed too: a judge entry with a number and no classification is "not judged" like any other missing classification, so it gets the judge's one retry and then goes to the implementer by rule 2; rules 7 and 8 have only their priority form. The judge's result kind is `judge` (was `score`), and on opencode its submit tool is `granny_submit_judgement` (was `granny_submit_score`).

### Fixed

- Checks: every check run records the HEAD it ran on (`checks[].head`). The final gate of a one-stage repo reuses the stage's last result only when HEAD is still that commit, and its log names the SHA; when a reviewer or the judge committed after the last gate, or HEAD could not be read, the checks run again. When the final check moves HEAD, the checks run once more without repairs (gate `pr-ready`); a red result sets `recheck: { passed: false, note }` and the branch is not PR-ready.
- Checks: granny never runs the checks on, or reviews over, uncommitted work. Every check gate reads `git status --porcelain` first; a dirty tree goes to the implementer as a commit prompt (`commit <stage> <gate> #<n>`) that spends a repair, and a tree still dirty when the budget is spent ends the gate `checks-failed` with `checks not run at <gate> - uncommitted changes: ...`. Without checks, a dirty tree after the implementer or a fix gets one commit prompt, and what stays uncommitted is named in the stage's or final review's note. After the `pr-ready` checks pass, a tree they left dirty sets `recheck: { passed: false }`; opencode's finish summary names both.
- Checks: the run's plan files inside the repo stay uncommitted, as the planner and plan-fix prompts require, so the status read leaves them out (`:(exclude,literal)` pathspecs) and the commit prompt and the final check's clean-tree rule tell the agent to leave them alone. Before, a plan fix that left `plan.md` changed with `worktree: false` cost a commit prompt at every gate and ended the stage `checks-failed`.
- Stages: an implementer that made no commit but left uncommitted work gets one commit prompt (`commit <stage> implement`) before the stage ends `no-changes`; with a commit then, the stage goes on to its checks and review. Still no commit, the `no-changes` note names the uncommitted files, and opencode's finish summary prints it.
- Claude Code: a `note` the granny helper adds to a command that ran stays out of the command's output; it is logged as `<label>: the helper's note, kept out of the command's output: ...`. Before, it was appended to the output, so a sentence note broke the stage's HEAD read and commit count (the review fell back to `<base>...HEAD` and an empty stage was not caught as `no-changes`), a one-word note such as `Done` became the review base, and a number in it could become a check's metric. The HEAD read now takes the first line that is a hex SHA and the commit count the first whole-number line.
- Checks: a working tree status read that fails is read once more and, failing again, is not taken for a clean tree. Before, granny logged `could not read the working tree status - going on without it` and went on as if nothing were uncommitted, so the checks ran, the review went ahead and the `pr-ready` recheck passed. Now a check gate fails at once with `checks not run at <gate> - working tree status unreadable (exit <code>: <output>)` and spends no repair, the `pr-ready` recheck sets `recheck: { passed: false, note: 'working tree status unreadable after the checks at pr-ready (...)' }`, and without checks the stage's note says the review may have missed uncommitted work; opencode's finish summary prints that line.
- Parallel stages: granny checks that a lane really merged (`git merge-base --is-ancestor <lane branch> HEAD`, label `verify merge <stage>`) before it reports the stage merged or cleans the lane up. Before, a `git merge` that failed without a conflict (uncommitted changes in the run's worktree, or a result the Claude Code helper misreported) went to the implementer as a conflict, passed the `MERGE_HEAD` probe, and the stage stayed `clean`; the cleanup then removed the lane worktree, `git branch -d` refused the unmerged branch, and the note said the worktree was left in place. Now a lane not in HEAD fails the run with `merge <stage>: <lane branch> is not merged into <branch> ...` and keeps its worktree and branch; the cleanup starts with the same check, and its note says what it removed and what it left (`its worktree <path> was removed, but its branch <lane branch> was left in place`, or both left in place with the reason).
- Review: residual findings of earlier rounds stay in the result. Before, `residual` held only the last round's, and nothing after a clean round or the round cap, so a finding scored at or below the threshold in round 1 - never sent to the fixer, so most likely still in the code - showed only in `history`. Now a review loop (a stage's review, the plan review, the final review) carries its residual over the rounds and returns it with `clean`, `residual-only`, `checks-failed` and `round-cap` (there without the last round's findings, which are `unresolved`). The judge's EARLIER ROUNDS block lists each round's residual findings too, under `r<n>/<id>` labels; a later finding it marks `repeatOf` one of them drops it when the repeat goes to the implementer and takes its place when the repeat is residual again, so each problem is listed once. A stage whose last round is clean stays `clean`, with the earlier residual in `residual`.
- Checks: a check with a `timeout` runs in `gtimeout` when `timeout` is not on PATH. granny looks once per run, before any agent starts, for `timeout` and then `gtimeout` (macOS with `brew install coreutils`) and wraps the checks in the one it finds; with neither, the run stops at once with an error naming the checks and `brew install coreutils`. Before, every such check exited 127 on macOS, which counted as a red check: both repairs were spent, the stage ended `checks-failed` and every later stage in that repo was skipped. A check with a timeout that still exits 127 with `timeout: command not found` is now a runner failure (note `timeout command not found`) and spends no repair.
- Review: a fixer declines a finding by id, and only a repeat of that finding can be dropped. The fix and plan-fix results take `declined: [{ id, reason }]` - the findings it did not fix on purpose, by the id it was sent; `deviations` stays free text for the report and does not drive routing. Before, any `deviations` text other than `none` marked the whole round declined: from the next round on P0/P1 findings went to the judge, and a repeated P1 scored at or below `threshold` was dropped as residual even when the fixer had fixed it and the deviation was about another finding (`applied it via the helper` was enough). Now P0/P1 findings go to the judge once a fixer declined one, but a repeated P0/P1 stays residual only when its `repeatOf` names a declined finding; every other P0/P1 goes to the implementer. An id the fixer was not sent is logged and ignored, a result without `declined` declines nothing, the judge's EARLIER ROUNDS block lists the declined labels with their reasons, the OVERRULED block quotes the fixer's reason per finding, and each round's `history` entry keeps its `declined`.
- Claude Code: the engine, not a helper agent, waits for a Codex or `command` review. Before, one helper ran the review script and was told to background it and wait, because a Bash call stops at 10 minutes; Haiku returned `ran: false` without waiting (the stage ended `review-failed`), and Sonnet polled with `pgrep -f`, which matched its own loop and never ended. Now the diff review and the plan review run in fixed helper steps: `review <stage> r<n> <name>` starts the script detached (`set -m; nohup bash -c ... &`, output, exit code and process group in `<workDir>/review-<stage>-r<n>-<name>.out`, `.exit` and `.pid`), `... wait <k>` polls the `.exit` file in the foreground for up to 9 minutes and prints `done` or `pending`, and `... read` prints the output with the review's exit code. After 7 waits (63 minutes) the engine stops the review and the reviewer did not run, so it gets its one retry. opencode still runs the script directly.
- Review: output without finding bullets is clean only when the no-findings sentence is all there is. Before, a `No findings.` (or `No material findings.`) line anywhere made it clean, so a finding written as prose or as a heading (`**P1** Null deref in src/a.ts:3`) disappeared when another section said `No findings.`, and the extraction never ran. Now only a leading `[granny] reviewer:` line and the Codex plugin's frame (its heading and `Target:` line, and in its structured render with `Verdict: approve` the summary paragraph and the `Next steps:` / `Reasoning:` lists) may surround the sentence; anything else goes to the extraction agent, which costs one call. A native Codex review that says in prose it found nothing (`No actionable regressions were identified. ...`) keeps going through that extraction.
- Stages: on a resume with `fromStage`, the first resumed stage that makes no new commit is reviewed over `<base>...HEAD` instead (logged `<stage>: no new commit on resume - reviewing <base>...HEAD instead`), with its checks first, and the stages after it run. Before, a stage whose commits were already on the branch from the interrupted run ended `no-changes` without a review and every stage that builds on it was skipped. With `<base>..HEAD` empty too it still ends `no-changes`; the later stages keep the rule that no commit means `no-changes`.
- Checks: a stage whose checks passed while the agent that last touched its code reported red gates now says so in its note: `the checks passed, but <who> reported red gates: <gates>`, where `<who>` is the implementer, the commit step, the last repair or the last fix, whichever reported last. The checks still decide the outcome, so the stage stays `clean` (or whatever its review made it); before, the report was only logged, so a gate the checks do not cover (`lint` red with only `bun test` as a check) vanished from the result. opencode's finish summary prints the line.

## 1.5.0

### Added

- **Checks** (`"checks": [{ name, run, maxRepairs?, timeout?, metric? }]`, default `[]`): commands granny runs itself instead of trusting the implementer's `gatesGreen`. They run after the implementer finished a stage, after every fix round (stage reviews and the final review), and once per repo on the whole branch before the final review, all before any review sees the code. A check passes when it exits 0 and, with `metric: { pattern, min?, max? }`, the last match's first capture group is a number within the bounds; `timeout` runs it as `timeout <s> bash -c '<run>'`.
- **Repair loop**: red checks go back to the implementer (`repair <stage> <gate> #<n>`) with their command, exit code, metric note and output tail, and the rule never to delete, skip or weaken a test, check, threshold, the granny config or a check script; then every check runs again. `maxRepairs` (default 2) caps the repairs per gate; a check's own `maxRepairs` overrides it. Repairs are not review rounds.
- Stage outcome `checks-failed`: the checks stayed red, so the review did not run or stopped; the stages that build on it, and the later stages of its repo when it left its red commits on the run's branch, are not started. A red stage that ran in its own worktree is not merged back; its lane branch and worktree are left in place. A red whole branch ends `finalReview` `checks-failed`, so the run is not PR-ready - it is repaired only when a final review follows and no stage of the repo ended `checks-failed`; the final check still runs. A stage whose checks ran is never `gates-red`. A one-stage repo with no lane merge reuses its stage's last check result at the final gate instead of running the same checks on the same HEAD again.
- `stages[].checks` selects checks by name (default all, `[]` none); an unknown name stops the run before any agent starts. A repo's whole-branch gate runs the checks its stages selected.
- The result records every check run: `stages[].checks`, and `checks` (also per repo in `repos`) for the whole-branch gate, each `{ at, attempt, results }`.
- On opencode the server executes the check commands; on Claude Code a granny helper agent runs each one and reports its exit code (phase "Checks"). A helper that returns nothing or no exit code gets one retry; then the gate ends `checks-failed` with `check runner failed`, without spending a repair.

### Changed

- A stage that runs in its own worktree branches from the commit the stage busy in the run's worktree started on, not from the run's branch tip, so its checks never run on that stage's unfinished commits.

## 1.4.0

### Changed

- **The default reviewer is the host's model**: without `reviewers` in the config, one `agent` reviewer named `reviewer` runs on the model selected in the host (pin one with `model` on the entry). Codex is an opt-in entry (`"engine": "auto"`, `"codex"` or `"codex-plugin"`); an entry that names no engine still means `auto`.
- Reviewers get the stage's task (`Stage N/M "name" ... its TASK`). They check the diff against it - a missing part is a finding, and so is a change outside it; work the task leaves to other stages is not - and report clean-code and design problems (duplication, naming, needless abstraction, deviations from the plan) as P2/P3. The judge scores findings against the task. Codex's built-in review takes no prompt, so only agent and command reviewers and the judge see the task.

### Added

- **Final review** (`"finalReview": true` by default): after every stage finished, each repo's whole branch (`base...HEAD`) goes through the review loop once more, before the final check, looking for cross-stage duplication and inconsistencies and checking merge commits and their conflict resolutions. Fixes land on the run's branch. A repo with one stage and no lane merge skips it; the result has `finalReview`, and each entry of `repos` its own. After `round-cap` or `review-failed` the final check still runs and the result says the branch has unresolved findings.
- **Declined findings stop coming back**: from round 2 on the judge sees the findings already sent to the fixer and the fixer's `deviations`. It marks a finding that repeats one with `repeatOf`; a repeat the fixer declined with a convincing reason scores low and stays residual for the user, a wrong reason is overruled and the fixer is told why. A first-time P0/P1 still goes to the implementer without the judge; once a fixer declined something, P0/P1 findings go through the judge too. A `deviations` text of "None" or "N/A" is not a decline.
- Stage outcomes `no-changes` (the implementer made no commit; nothing is reviewed and the stages that build on it end `skipped`) and `gates-red` (the review found nothing to fix but the gates were left red).

### Fixed

- A stage is `clean` only when a review looked at real changes. Granny reads HEAD itself before the implementer runs and reviews from there, not from the `startSha` the implementer reports. Reviewer output with no finding bullets is clean only when it says "No findings." (or the Codex plugin's "No material findings."); anything else goes to the extraction agent, which must find the findings or confirm a clean review, otherwise the reviewer did not run.

## 1.3.0

### Added

- **Parallel stages**, on by default (`"parallel": true`, at most `maxParallel` stages at once, default 3). A stage waits only for the stages in its new `after` list (1-based, earlier stages only); without `after` it waits for the previous stage in its repo, so existing stage lists run as before. `"parallel": false` runs one stage at a time in list order.
- **Several repos in one run**: `repos` lists the other repos (paths, or `{ repo, base }`) and a stage names its repo with `repo`. Each repo gets its own worktree on the run's branch, every prompt names the other repos and forbids touching them, and the final check runs in every repo; the result has `repos: [{ repo, base, worktree, final }]` and each stage in another repo carries `repo`. On opencode the preflight checks every stage repo.
- **Parallel stages in one repo**: a stage whose repo is busy runs in its own worktree on `<branch>--s<N>-<stage-slug>`, is implemented and reviewed there, then merged into the run's branch once no stage works there (`git merge --no-edit`). On a conflict the implementer resolves the merge; a merge left unfinished fails the run. The lane worktree and branch are removed after a clean merge. The lane's PR-body notes go to `<workDir>/PR-BODY-s<N>-<stage-slug>.md` in the run's worktree, and the final check folds them in.
- The planner sets `after` on every stage so independent work runs in parallel, and with `repos` it explores those repos and gives each repo its own stage.
- When a stage throws while others run, nothing new starts, the running stages finish, then the run fails with that error.

## 1.2.0

### Added

- **Planner**: a run with `goal` instead of `stages` plans the work first. A new `planner` role (`roles.planner`, session model by default) explores the repo in the worktree, writes the plan - to `plan`, or by default to the main checkout's git-excluded `<workDir>/plans/<branch-slug>.md` - with work orders and acceptance criteria, and proposes the stages. With `"planReview": true` the plan review runs on it. The run stops with `draft` (`{ files, stages, summary, questions? }`) in its result and nothing implemented; after the user approves, a second run with `plan` and the approved `stages` implements it. A planner that returns no plan file or no stage fails the run. On opencode the planner answers through `granny_submit_plan`; on Cursor through the new `granny-planner` subagent.

- opencode: install the plugin globally. With `worktree` on, a per-project install in `<project>/.opencode/plugins/` is missing in the worktree where the role sessions run, so they have no `granny_submit_*` tools and fail.

## 1.0.0

The first release of granny-workflow: an agent skill that takes a plan to a PR-ready branch through an implement → review → judge → fix loop, and stops without pushing.

### Hosts

- **Claude Code**: a Workflow script (`engines/claude-code/workflow.js`). Every role is an `agent()` call with its own model, effort and JSON schema; resume with `resumeFromRunId` or `fromStage`.
- **opencode 2.x**: a server plugin (`engines/opencode/plugin/granny-workflow/`) with `granny_run`, `granny_status` and `granny_cancel`. Every role is a child session with its own model and permissions; `granny_cancel` interrupts every running child session and stops every review command with its whole process group.
- **Cursor and other agents**: the same loop as a manual protocol with three subagents (`granny-implementer`, `granny-reviewer`, `granny-judge`).

### The loop

- Stages: the implementer builds each stage and commits with the gates green; every stage is reviewed against its start sha, `review: false` skips the review and `implement: false` reviews work that is already written.
- Reviewers: any number, all reviewing every round in parallel. Engines `auto`, `codex` (the Codex CLI), `codex-plugin` (OpenAI's Codex plugin for Claude Code, including its adversarial review with `mode` and `focus`), `agent` (a host model with its own model and effort) and `command` (any CLI, with the `{base}`, `{out}`, `{model}` and `{prompt}` placeholders).
- Each reviewer has its own output files, log lines, finding ids (`<reviewer>-F<n>`) and Codex plugin broker, which it stops when its review ends.
- A reviewer that does not run is run once more; when it fails again the stage ends `review-failed`, naming it, with the other reviewers' findings kept as unresolved.
- Judge routing: P0/P1 findings go straight to the implementer and never reach the judge. The judge scores the rest 0-100 and merges duplicates; findings above `threshold` (default 70) are fixed, the rest are reported as residual. `maxRounds` (default 4) caps the reviews per stage.
- Review output is read from Codex-style `- [P1] Title — path:line` and `- [high] Title (path:line)` lines; when the parser comes up short a helper agent extracts the findings, and a review that still cannot be read ends the stage `review-failed` instead of reading as clean.
- Worktree (on by default): the run works in the branch's own git worktree, reusing the one that has the branch checked out or creating one under `worktreeDir`; a dirty reused worktree stops the run before any agent starts. Granny never removes it.
- Plan review (on by default when the run has `plan`): the same reviewers, routing and round cap check the plan files against the repo before stage 1; the implementer fixes accepted findings in the plan files in place, under a dated `rN deltas` section, without committing them. A plan review that ends `round-cap` or `review-failed` stops the run before anything is implemented.
- Final check: gates, a clean tree, no AI attribution in commits, and the PR body at `<workDir>/PR-BODY.md`. Nothing is ever pushed.

### Config

- Three layers, later wins: `~/.config/granny/config.json`, `<repo>/granny.config.json`, and the run's overrides. Unknown keys and invalid values stop the run before any agent starts, with every problem and its path listed.
- Keys: `roles` (`granny`, `implementer`, `judge`), `reviewers`, `threshold`, `maxRounds`, `planReview`, `base`, `gates`, `workDir`, `worktree`, `worktreeDir`, `language`, `aiAttribution`, `rules`. Models are one string or an object keyed by host.
